## BUG-001 · 跨平台年化口径不统一（8 小时一刀切）

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-16 |
| 模块 | `quant 探索` 跨平台费率对比（scan_dex_multi / scan_dex / monitor_dex / 看板） |
| 严重度 | **高**（结论层面错误，不是显示瑕疵） |
| 发现者 | **示例用户**（用 Backpack App 实际盘面核对出来的） |

### 现象
`🌐 多平台` 页里，Backpack 的 BTC 年化显示 **−4.89%**；
而 Backpack App 里同一个 BTC-PERP 写着 **资金年化利率 −39.2030%**。
**差了整整 8 倍。**

### 根因
年化函数里把**所有平台**都当成"**每 8 小时结算一次**"：

```python
annual = rate * (24 / 8) * 365 * 100     # ← 写死了 8
```

而实际结算周期各家不同：

| 平台 | 真实周期 | 依据 |
|---|---|---|
| hyperliquid | **1 小时** | https://hyperliquid.gitbook.io/hyperliquid-docs/trading/funding |
| lighter | **1 小时** | https://docs.lighter.xyz/trading/funding |
| backpack | **1 小时** | 接口 `info.fundingInterval = 3600000` ms |
| aster | **8 小时** | https://www.asterdex.com/en/futures/futures-info/real-time-funding-rate |
| paradex | **8 小时** | 接口返回 `interval = 8h` |

**三家被放大了 8 倍的分母**，所以年化被缩小了 8 倍，排序随之失真。

### 修正
新增 `funding_hours(label, rate_dict, market)`，按优先级取周期：

1. `fetch_funding_rate()` 返回的 `interval` 字段（如 `"1h"` / `"8h"`）
2. `market["info"]["fundingInterval"]`（毫秒 → 除 3600000）
3. 兜底表 `FALLBACK_HOURS`（依据上表，注了出处）
4. **都取不到 → 返回 None，宁可显示"—"，不猜**

已应用到：`scan_dex_multi.py`、`scan_dex.py`、`monitor_dex.py`、`看板\app.py`。

### 修正后（2026-09-16）
Backpack BTC **−39.35%**，与 App 的 −39.20% 对齐（费率本身会波动）。

### 教训
> **跨平台比较任何"年化"数字之前，先对齐口径——问一句"多久结一次"。**
> 口径不对，比较的是假象，而且错得很隐蔽（数字看起来都挺合理）。

### 证据
- 用户截图：Backpack BTC-PERP，资金年化利率 −39.2030%
- 本地存档：本仓 `数据\监控\dex_multi_history.csv`（修正后）
- 探针脚本：`脚本\test_funding_interval.py`、`test_funding_interval2.py`

## BUG-002 · 只思考不落正文（API 请求被掐断）

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-16 ~ 09-17 |
| 模块 | 会话输出（agent 层） |
| 严重度 | **中高**（表现为“思考完成”但正文一个字没有） |
| 发现者 | **示例用户**（截图）“怎么思考了不输出” |

### 现象
界面上连着几轮显示“思考完成”，**正文空白**；用户发消息也无回应。

### 排错过程
把会话 JSONL（`<HanaAgent目录>\agents\hanako\sessions\*.jsonl`）拆开统计：

- assistant 轮共 **546** 轮
- 真正的“有思考、无正文、未调工具”——**只有 2 轮**
- 这 2 轮以及另外 3 轮，共 **5 条记录 `stopReason = error`、`usage` 全为 0**
- `errorMessage` 为 **`terminated`** 或 **`Request timed out.`**

| 记录 | 报错 | 内容块 |
|---|---|---|
| #33 | `terminated` | 只有 `think(3)`（“Let”就被掉断）|
| #71 | error | think+text（部分）|
| #95 | error | 只有 think |
| #148 | `terminated` | **完全空** |
| #298 | `Request timed out.` | **完全空** |

### 根因
**不是“输出太长被截”，也不是模型忘了写正文。**
是 **API 请求本身被终止/超时**，返回 0 字——所以那一轮什么都没产生。

**关键规律：5 次全部发生在 `toolResult` 之后的那一次续跑请求**（#32→#33、#147→#148、#297→#298…）。
推断：
- 工具返回体量大 → 上下文膨胀 → 请求变慢
- 叠加长会话（本例 1228 条记录 / 4MB）→ 更容易撞上超时

### 修正 / 对策
改行为，不改代码（平台无超时/重试设置项）：

1. **控制单次工具返回的体量**：`read` 加 limit、先用 `grep`/`find` 定位，别整文件倒进上下文。
2. **别让会话无限长**：跨话题及时**开新会话**或压缩，缩短上下文。
3. **出现空轮时的应急**：用户**直接再发一句**（哪怕“继续”）通常就能接上。
4. 每轮**尽量保证有正文**；宁可短，不留空。

### 证据
- 会话日志中的 #33 / #71 / #95 / #148 / #298 记录
- 探针脚本：`脚本\_inspect_session*.py`
